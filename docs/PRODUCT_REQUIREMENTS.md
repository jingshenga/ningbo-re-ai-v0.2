# 产品需求文档 PRD — 宁波房产AI情报与智能选房平台

版本：V0.2（2026-11-09）。定位：先运营者内部使用，后向宁波购房者提供免费智能找房及经授权的撮合服务。

## 1. 核心问题与目标
传统挂牌网站能看到不少房源，但跨平台重复、报价不一致、降价线索滞后、短视频线索不结构化；大模型没有稳定真实的本地房源和报价历史时，回答“某小区某栋某楼某个价是否划算”只能泛化推断。本产品的护城河应是**证据完整的宁波本地实时数据、同源价格历史、严格的同套匹配、持续条件单**，而不是通用聊天功能。

## 2. 角色与场景
- 运营者：设置监控账号、查看采集健康、上传网页样本、复核候选、维护小区别名、设定数据保留策略。
- 购房者（未来）：用自然语言提出区域、预算、面积、房型、用途、楼层和通勤要求；比较多套候选，订阅新房源/降价提醒。
- 合作中介（未来）：在客户授权后确认信息是否有效、联系卖方、协助带看及交易，不得未经用户许可共享需求或联系方式。

## 3. 核心用户任务与验收
### F1 账号监控
输入抖音主页URL/可用唯一ID，设定每2小时检测、首轮历史补采 none/30d/90d；新增视频去重入库，保存同步记录。微信视频号先支持人工客户端导出，平台自动连续监控为后续可研。**验收：同源视频100次重复导入只有1条、被限制时标记partial/failed。**

### F2 网页房源来源
贝壳、安居客以“可解析的公开页面／保存HTML样本”为当前技术路线。来源信息进入待审核队列；未来如获授权可替换为正式接口。在线操作必须符合访问规则和权限审查。**验收：记录source/URL/来源ID/采集时间/哈希/审核状态；未获批时不发网络请求。**

### F3 视频信息抽取
转写音频、抽帧OCR；提取小区名、面积、价格提及、户型、楼层、装修、地理线索，记录文本位置和置信度。视频发布地与房子位置分开。**验收：价格冲突进入待核对，不写正式挂牌历史。**

### F4 同源去重及跨渠道候选
同平台同ID直接去重；跨平台只做候选相关，不在证据不足时确认同一套。后续增加图片相似度和人工审核。**验收：多个相似房源不能误合并。**

### F5 挂牌价格历史
区分平台挂牌价、视频口头价、成交价；同源同ID报价形成可追踪快照。**验收：历史回填不会覆盖当前报价，同日不同价冲突需人工审核。**

### F6 找低价和降价
第一版机会包括7/30/90日幅度降价、同可比样本价差、跨渠道报价冲突、稀缺条件匹配。不能以“远低于小区均价”代替正规估值。**验收：样本不足时不给出确定低估百分比。**

### F7 购房条件单与提醒
输入目标区域、总价上限、面积下限、至少几室、指定小区、降价阈值；后续增加硬/软条件和排除项；提醒按房源事件去重。**验收：同一条降价对同条件单最多一条事件，提醒不误宣称已正式发送。**

## 4. 非功能需求
- 部署：绿联DXP4800 16GB RAM Docker；N100 CPU；初期每日小批量、低并发。
- 可靠性：PostgreSQL有卷持久化、每日备份，数据库迁移可重复执行；崩溃后任务可恢复。
- 安全：单操作者API Key仅限NAS或局域网使用，禁止公网直出；后续补RBAC和用户隔离。
- 可解释性：机会评分必须展示由哪些来源、可比样本数、价格时间组成。
- 数据质量：可存证、可更正、可撤销、可标记过期；避免收集无必要的联系方式和个人信息。

## 5. MVP范围与不做事项
V0.2包括后台API和采集候选处理能力，不包括真正从贝壳、安居客批量在线获取成功的承诺、视频号无人值守、自动ASR/OCR、完备估值模型、公网多用户系统或商业撮合支付。

## 6. 业务阶段
内部数据验证→小范围试点→房源订阅和条件单→可解释推荐→合规公开产品→授权中介撮合。每个阶段以准确性、权限条件和经营成本为门槛，不靠扩大抓取量解决数据质量问题。
