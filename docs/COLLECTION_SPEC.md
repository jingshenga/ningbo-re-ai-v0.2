# 贝壳与安居客采集技术规格 V0.2

## 1. 现实前提
当前没有可用的授权API。研发方向是可替换的公开页面采集器；**当前V0.2已实现的是保守通用解析、网页样本导入、人工审核、显式权限检查和按目标尝试抓取的基础框架，不代表已对两个网站真实采集成功。** 贝壳/安居客专用稳定解析器和真实页面联调仍待完成。

## 2. 两条数据通道
- **当前通道 `public_page_collection`**：URL登记 → 检查来源规则/robots → 允许则抓取HTML → SHA256证据 → 抽取候选 → 人工复核 → 正式挂牌与历史价格。
- **未来通道 `licensed_api`**：若以后拿到合同及接口，则新适配器输出同样字段；不能假定已有授权或接口。

## 3. V0.2 已实现工作流
1. 本地HTML样本经 `POST /api/collection/pages` 上传，无任何网站网络请求。
2. `parse_listing_html` 只识别明确标签及详情页可识别ID，字段冲突/不完整留空；数值字段按数值等值比较，格式不同但值相等的重复标注不视为冲突，面积/价格只接受规范的逗号千分位，格式损坏的数字不会中断解析且与有效值并存时按冲突处理；页面声明的canonical URL/`og:url`若含不同来源ID，则挂牌ID留空并追加告警。解析前移除语义侧栏`aside`、HTML`hidden`属性和最终内联`display:none`元素；单独的`aria-hidden=true`只影响辅助技术，不视为视觉隐藏，避免推荐卡片/隐藏内容报价污染详情字段。样本清单/评估器、解析器和API均要求HTML为严格有效UTF-8，并限制HTML为1,000,000 UTF-8字节；本版不猜测或自动转码，解析规则版本保存在候选中。
   `source_url`长度为12–2000字符且不得包含userinfo、查询参数或片段，以免将凭据、跟踪数据/临时令牌写入候选；canonical URL仅用于来源ID核对，核对时忽略其查询参数和片段。
3. `collection_candidates` 写入来源、URL、解析版本、提取结果、告警、原始HTML哈希及gzip证据文件；`field_evidence`记录文本属性与source ID的候选片段/来源/字符偏移，每字段最多20条并标注总命中数/是否截断；URL ID指出提交URL或canonical来源，canonical命中不保存查询参数、片段及路径前缀。冲突字段保持空值但仍返回命中证据，置信度明确未校准。人工更正更新对应字段出处为`manual_review`并清除旧解析命中。
4. `PATCH /api/collection/candidates/{id}` 人工补正字段（需理由）。
5. `POST /api/collection/candidates/{id}/review?decision=approve&note=...` 事务中正式入库，同ID价格变化生成历史记录。拒绝也需原因。
6. `collection_targets` 可登记并按周期检查；列表目标由Worker按持久化游标分页，每轮最多处理5个列表页和20个详情页候选。已见来源ID会跳过；普通错误保留重试游标供后续周期续跑，策略阻断即使发生在首个详情暂存前也会保留活动扫描状态与当前列表页游标。robots或上游阻断会禁用目标并保留状态。来源政策+全局开关默认都关闭，未获允许时只记 `blocked_policy`，不发请求。此流程已由mock测试覆盖，并有隔离PostgreSQL集成用例；该集成用例尚未运行。

## 4. 必须遵守的采集边界
- 不使用绕过验证码、登录验证、动态签名、访问限制、代理轮换或反风控技术。
- 不试探第三方私有接口，不抓取需认证的个人隐私页；不假冒登录用户。
- 使用HTTPS+域名白名单，拒绝跨域跳转。`robots.txt`不确定/不可读时保守阻断。
- 401/403/429、重定向或HTTP 200验证码/反爬挑战页时记录`blocked_upstream`，不重试或切换出口规避；挑战页正文不进入候选、不写入错误信息。
- 未来若获得允许在线采集的证据，运营者记录 `source_registry` 的审查依据，并显式设置 `ENABLE_ONLINE_COLLECTION=true`，仅访问许可范围内的目标。
- Worker先在请求`robots.txt`前核对全局开关和来源许可；robots允许后，再于真正请求房源列表页/详情页前复核一次。权限查询事务均在相应网络请求前关闭，避免慢速页面抓取期间持有来源行锁。若许可在robots响应期间撤销，房源页请求会被阻断；已经发出的单次HTTP请求不会被中途取消。
- 不能把权限审核仅当做一个程序开关；实际内容储存、对外传播和商业使用还需独立核实。

## 5. 列表发现与详情抓取必须分开
- **通用发现器与Worker分页已实现**：在全局及来源权限门通过后，从登记的列表页发现同源详情URL和来源ID，持久化分页游标与已见ID，并只抓取详情页进入候选审核；每轮最多5个列表页和20个详情页。当前仅经合成页面/mock服务验证，隔离PostgreSQL集成用例尚未运行，真实来源许可和页面样本未提供。
- **详情器（V0.2只有基础框架）**：单详情URL → HTML证据/抽取候选 → 人工审核。禁止把列表页的推荐卡片、广告和侧边栏报价当作某套房详情价。
- 后续优先从用户给定的小区/房源链接、明确许可的站点入口开始，而不是一开始全城全量遍历；不合法或不可访问的列表发现必须保持禁用。
- 仍需建设独立的“待发现URL队列、首次发现/最近看到时间、下架待核验状态”，当前游标和已见ID不能确认挂牌失效或下架。

## 6. 站点专用解析器待开发
- `beike.py`: 从真实保存的宁波详情页定位稳定房源ID、区域、小区、面积、户型、总价、楼层/朝向、图像与状态。页面布局变化必须由测试发现。
- `anjuke.py`: 独立处理标题、字段布局、房源ID、时间、同源变价，失败不可静默混入数据。
- 每站至少20条合规来源的人工审查样本，覆盖正常/多价/无价/下架/缺ID/迁移/重定向/重复房源。
- 指标：字段准确率（在有答案的样本上）、有效字段覆盖率、错误地把房源合并成同套的比例、每条有效审核房源的处理成本。

## 7. 任务失败状态
`blocked_policy`（运营者未授权或总开关关闭）、`blocked_robots`（robots不允许或不可确认）、`blocked_upstream`（403/429/登录/重定向等）、`failed`（解析/网络/数据异常）、`success`（保存一个候选，**不是最终房源审核通过**）。

## 8. 避免误导性价格
- 网页同页多处出现“365万/390万”时禁止自动选择“最新”价格；户型、区域、楼层或装修出现多个不同标注时字段留空并输出对应冲突告警；样本清单须以对应场景标签标出歧义，评估器同时核验留空及告警。
- 从搜索页、广告模块或推荐房源区找到的价格不应当被当成详情页本套挂牌价。
- 发布日期/抓取日期/价格更新时间分开。真实成交只通过可信成交数据源接入。
- 字段缺失不猜测；采集成功仅代表保存了候选证据。
